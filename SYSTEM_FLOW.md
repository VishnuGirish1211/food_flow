# FoodFlow — Complete Request & Saga Flow Trace

> An exact, step-by-step trace of how a request moves through every service, every
> database transaction, every Kafka event, and every saga branch.
>
> **Structure per service:** Database Tables → HTTP Layer → Background Producer →
> Background Consumer → Anything Else.

---

# PART 0 — SYSTEM TOPOLOGY

## 0.1 The four services

| Service | Container | Port | Database | Kafka role |
|---|---|---|---|---|
| **Auth** | `auth-service` | 8001 | `auth_db` | none — no events at all |
| **Order** | `order-service` | 8002 | `order_db` | saga initiator + terminator |
| **Restaurant** | `restaurant-service` | 8003 | `restaurant_db` | saga participant (stock) |
| **Payment** | `payment-service` | 8004 | `payment_db` | saga participant (money) |

Every service owns **exactly one database** and never opens a connection to another
service's database. There is **no shared schema, no shared table, and no foreign key
across a service boundary.** Cross-service consistency is achieved only through Kafka
events.

This is the constraint that forces the saga pattern to exist. The moment you have four
separate databases, `BEGIN … COMMIT` can no longer span the business operation, so a
distributed rollback has to be built by hand out of compensating events.

## 0.2 Infrastructure

| Component | Image | Purpose |
|---|---|---|
| **nginx** | `nginx:alpine` | Single public entry point on host port **8085** → container 80. Path-based reverse proxy. |
| **postgres** | `postgres:16-alpine` | One instance, **four logical databases**. Host port 5432. |
| **kafka** | `cp-kafka:7.5.3` | KRaft mode (no ZooKeeper). Internal listener `kafka:9092`, host listener `localhost:9093`. |
| **redis** | `redis:7-alpine` | Used by **Auth only**, for rate limiting. Host port 6379. |

**Startup ordering** is enforced by `depends_on` plus healthchecks: Postgres must pass
`pg_isready`, Redis must answer `PING`, and Kafka must answer `kafka-topics --list`
before any service container starts. This prevents a service booting into a connection
storm against a not-yet-ready broker.

Kafka runs single-broker, so every replication setting is pinned to 1
(`OFFSETS_TOPIC_REPLICATION_FACTOR`, `TRANSACTION_STATE_LOG_MIN_ISR`,
`TRANSACTION_STATE_LOG_REPLICATION_FACTOR`) and
`GROUP_INITIAL_REBALANCE_DELAY_MS=0` so consumer groups form instantly instead of
waiting out the default 3-second rebalance delay.

## 0.3 The complete event catalogue

There are **six** event flows in the entire system. Every one of them is written to a
database outbox table first and published by a relay second — **no service ever calls
the Kafka producer directly from a request handler or a consumer handler.**

| # | Topic | Produced by | Consumed by | Meaning |
|---|---|---|---|---|
| 1 | `order.placed` | order-service | restaurant-service | Saga started. Try to reserve stock. |
| 2 | `stock.reserved` | restaurant-service | payment-service | Stock is deducted. Take the money. |
| 3 | `stock.rejected` | restaurant-service | order-service | Not enough stock. Saga aborts. |
| 4 | `payment.succeeded` | payment-service | order-service | Money captured. Saga completes. |
| 5 | `payment.failed` | payment-service | order-service | Money not captured. **Compensate.** |
| 6 | `stock.release` | order-service | restaurant-service | **The compensating transaction.** Give the stock back. |

Consumer group subscriptions:

| Consumer group | Subscribes to |
|---|---|
| `restaurant-service` | `order.placed`, `stock.release` |
| `payment-service` | `stock.reserved` |
| `order-service` | `payment.succeeded`, `payment.failed`, `stock.rejected` |

## 0.4 The event envelope

Every message on every topic has an identical outer shape, produced by one shared helper:

| Field | Type | Generated by | Purpose |
|---|---|---|---|
| `event_id` | UUID v4 string | the wrap helper, at outbox-write time | **The idempotency key.** This is what every consumer stores in `processed_events`. |
| `event_type` | string | caller | The dot-separated topic name; consumers branch on this. |
| `occurred_at` | ISO-8601 UTC | the wrap helper | When the *business fact* happened, not when it was published. |
| `payload` | object | caller | Event-specific data. **Always contains `order_id`** — the saga correlation ID. |

The critical detail: `event_id` is generated **once**, at the moment the outbox row is
written, and is then frozen inside the JSONB payload. If the relay publishes the same
row twice, both copies carry the *same* `event_id` — which is exactly what makes
duplicate detection possible downstream.

## 0.5 nginx routing table

nginx does path-prefix routing only. It does **not** terminate TLS, load balance, rate
limit, or cache — all deliberately out of scope.

| Public path | Upstream | Note |
|---|---|---|
| `/auth/` | `auth-service:8001/` | The **trailing slash** on the upstream strips the `/auth` prefix, so `/auth/login` reaches the service as `/login`. |
| `/orders` and `/orders/` | `order-service:8002` | **No trailing slash** on the upstream, so the full path is preserved: `/orders` arrives as `/orders`. Two separate location blocks exist because `location /orders/` does not match the bare `/orders` that `POST` uses. |
| `/restaurants`, `/restaurants/` | `restaurant-service:8003` | Same prefix-preserving pattern, same two-block trick. |
| `/payments`, `/payments/` | `payment-service:8004` | Same. |

On every proxied request nginx injects three headers: `Host`, `X-Real-IP`
(`$remote_addr` — this is what Auth's rate limiter keys on), and **`X-Request-ID`
(`$request_id`, nginx's own per-request UUID)**. That last one is what makes a single
customer request traceable across all four services' JSON logs.

## 0.6 Database bootstrap

`scripts/init-databases.sql` is mounted into `/docker-entrypoint-initdb.d/` and runs
**once**, on the very first start of the Postgres volume. It does nothing but
`CREATE DATABASE` four times — `auth_db`, `order_db`, `restaurant_db`, `payment_db`.
It never runs again; re-running requires deleting the `postgres_data` volume.

Schema itself is **not** created here. Each service runs its own migrations, in-process,
at startup (see §1.1).

# PART 1 — SHARED MECHANISMS

These mechanisms are identical in every service that has them. They are described once
here in full detail, then referenced by name in each service section.

## 1.1 Startup and in-process migrations

Every service's `lifespan` begins the same way:

1. **`setup_logging(<service-name>)`** — configures structlog with a fixed processor
   chain: merge contextvars → add log level → ISO timestamp → stack info → exception
   formatting → **JSON renderer**. Output goes to stdout as one JSON object per line.
   Then `service=<name>` is bound globally.

2. **Create the connection pool** — `min_size=2, max_size=10` against the service's own
   `DATABASE_URL`. Every connection the pool creates runs an `init` hook that registers a
   **JSONB type codec** (a `json.dumps` encoder and `json.loads` decoder bound to
   `pg_catalog`). Without this, asyncpg would hand back JSONB columns as raw strings;
   with it, Python dicts and lists round-trip transparently. This is what allows the
   outbox payload and the order items to be written and read as native Python objects.

3. **Migrations run against that pool.** The service's `migrations/` directory is globbed
   for `*.sql` and the filenames are **sorted lexically** — which is why they are named
   `001_`, `002_`. Each file's entire contents are executed as one statement batch, and
   each application is logged as `migration_applied`.

   **There is no schema-version table.** Idempotency is achieved purely by writing every
   statement as `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`,
   `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, or `INSERT … ON CONFLICT DO NOTHING`.
   Re-running the full set against an already-migrated database is a harmless no-op.

   **The trade-off:** this scheme cannot express a destructive migration — a rename, a
   drop, a data backfill — because those are not naturally idempotent. Those would need a
   real versioning table.

## 1.2 The transactional outbox — why it exists

Every event-producing service has an `outbox_events` table with an identical shape:

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID PK, `gen_random_uuid()` | Row identity. **Not** the `event_id` — that lives inside `payload`. |
| `topic` | VARCHAR(255) NOT NULL | Kafka topic name. |
| `key` | VARCHAR(255) | Kafka partition key = the `order_id` string. |
| `payload` | JSONB NOT NULL | The complete frozen event envelope. |
| `created_at` | TIMESTAMPTZ NOT NULL, `NOW()` | FIFO ordering for the relay. |
| `published_at` | TIMESTAMPTZ **nullable** | NULL = pending. Non-NULL = sent. This single column is the whole state machine. |

Plus a **partial index**: `ON (created_at) WHERE published_at IS NULL`.

This is deliberate and important. The relay polls this table once per second, forever.
Because the index contains only unpublished rows, published rows fall out of it
automatically and the index stays permanently tiny regardless of how many million events
have flowed through. A plain index on `created_at` would grow without bound and the poll
would degrade over time.

### The problem the outbox solves

The naive approach is: commit the business row, then send to Kafka. That has two failure
modes and neither is fixable:

- **Crash after commit, before send** → the row exists but no service is ever told. The
  saga is silently lost. The order sits in `PENDING` forever with nothing to advance it.
- **Send succeeds, then commit fails** → downstream services begin reserving stock and
  charging money for a business fact that does not exist in any database.

You cannot make a Postgres commit and a Kafka publish atomic. There is no distributed
transaction between them, and a two-phase commit across them would be both unavailable
and operationally unacceptable.

**The outbox sidesteps the problem entirely** by making *the intent to publish* part of
the same transaction as the business fact. Both rows commit or neither does; Postgres's
own atomicity does all the work. The actual Kafka publish then becomes a **separate,
retryable, at-least-once** concern — and because it is driven off a durable table row,
"not yet published" is a *recoverable state* instead of *lost data*.

## 1.3 The outbox relay — the background producer

Started at boot as an asyncio task on the same event loop as the HTTP server. The code is
identical in Order, Restaurant, and Payment.

### Outer loop

`while not shutdown_event.is_set():`

- Call the inner drain function; it returns a count of events published.
- **If count is 0**: instead of a plain one-second sleep, it awaits
  `shutdown_event.wait()` with a 1-second timeout. This is an **interruptible sleep** — a
  normal quiet second raises a timeout which is swallowed, but if shutdown is signalled
  during that second the wait returns immediately. Shutdown is never delayed by a sleep
  already in progress.
- **If count is greater than 0**: skip the wait entirely and loop straight back. Under a
  burst the relay runs hot with zero polling delay.
- **Any exception** in the whole cycle is caught, logged as `outbox_relay_error`, then a
  one-second backoff. **The loop can never die.** A Kafka outage degrades to
  retry-forever, not to a dead relay and a permanently stalled saga.

### Inner drain loop — one event per transaction

Loops until it finds nothing. Each iteration opens a transaction and runs:

> `SELECT id, topic, key, payload FROM outbox_events WHERE published_at IS NULL ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`

Clause by clause, because every piece is load-bearing:

- **`WHERE published_at IS NULL`** — hits the partial index; only the pending working set
  is ever scanned.
- **`ORDER BY created_at`** — FIFO. For a single order, `order.placed` was written before
  `stock.release`, so it publishes first.
- **`LIMIT 1`** — one event per transaction, deliberately. If the Kafka send fails, only
  *that one* event rolls back. A batch would roll back sends that had already succeeded.
- **`FOR UPDATE`** — takes a row-level write lock. A second replica's relay cannot select
  the same row.
- **`SKIP LOCKED`** — instead of *blocking* on a row another relay holds, skip it and take
  the next one. Without `SKIP LOCKED`, N relay replicas would serialize behind each other
  and total throughput would equal that of a single relay. With it, N replicas grab N
  different rows and drain in parallel. **This clause is what makes the relay
  horizontally scalable.**

If the SELECT returns nothing → break out of the drain loop, return the count.

Otherwise, **still inside the open transaction**:

> **Send to Kafka and wait for the broker acknowledgement**, with the row's topic, the
> UTF-8 encoded key, and the payload as the value.

This send blocks until the **broker acknowledges**. It is not fire-and-forget. If the
broker is down or the send times out, this raises — the transaction rolls back, the row
lock releases, `published_at` stays NULL, and the very next poll picks the same row up
again. **The event is never lost.**

The `key` is the `order_id`. Kafka hashes it to select a partition, so **every event for a
given order lands on the same partition**, and Kafka guarantees ordering within a
partition. This is precisely why the restaurant service can never observe `stock.release`
before `order.placed` for the same order.

The `value` is the envelope dict; the producer's JSON serializer encodes it to bytes.

> `UPDATE outbox_events SET published_at = NOW() WHERE id = $1`

Then **COMMIT**. Increment `outbox_events_published_total`, log `outbox_event_published`,
loop for the next row.

### The at-least-once window — deliberate, not a bug

There is an unavoidable gap: Kafka has acknowledged the message, but the `UPDATE` has not
yet committed. Kill the process exactly there and the row is still `published_at IS NULL`,
so on restart **the same event is published to Kafka a second time** — carrying the
*same* `event_id`, because the envelope was frozen into the payload at write time.

This is accepted, not prevented. The system is **at-least-once, never at-most-once**:
losing a saga event is catastrophic, publishing one twice is harmless — *because* the
identical `event_id` is caught by every consumer's `processed_events` primary key.

> **The outbox and the idempotency ledger are two halves of one design. Neither works
> alone.** The outbox guarantees an event is never lost, at the cost of sometimes sending
> it twice. The ledger absorbs the duplicates. Remove either half and the system breaks.

## 1.4 The consumer pattern — the background consumer

Order, Restaurant, and Payment each own their consumer outright — no shared base class,
no inheritance. But the loop shape is identical.

### Consumer configuration

The shared factory builds a consumer with:

- **`group_id`** = the service name. All replicas of a service share one group, so Kafka
  assigns each partition to exactly one replica — scaling out **splits** load rather than
  duplicating it. Different *services* use different group ids, so each service receives
  its own independent copy of every event on a topic it subscribes to.
- **`auto_offset_reset="earliest"`** — a brand-new consumer group reads from the beginning
  of the topic, so events published before the service first started are not skipped.
- **`enable_auto_commit=False`** — **critical.** With auto-commit, Kafka advances the
  offset on a timer regardless of whether processing succeeded, and a crash
  mid-processing would silently drop the event. Manual commit means the offset moves only
  after the work is durably done.
- A JSON value deserializer: bytes → dict.

### The polling loop

`while not shutdown_event.is_set():`

- **Fetch a batch with a 1000 ms timeout**, returning a mapping of topic-partition to
  message list. The 1-second timeout is what makes shutdown responsive: the loop
  re-checks the shutdown flag at least once per second even when the topics are
  completely silent.
- Iterate partitions, then messages within each partition (partition order is preserved).
- Each message goes to the service's message handler **wrapped in its own try/except**:
  - success → `kafka_messages_consumed_total{topic, status="success"}` incremented
  - exception → full traceback logged as `consumer_error`, then `status="error"`
    incremented. **The loop continues.** One poison message cannot stall the consumer.
- **After the whole batch**, if anything was fetched: commit the offsets.

**Consequence of committing after the batch:** the offset advances past *every* message in
the batch, including any that raised. A permanently-failing message is effectively
**skipped**, not retried — and there is no dead-letter topic, so the failure exists only
as a log line and a metric increment. Conversely, if the process dies mid-batch before the
commit, the **entire batch is redelivered** — which is exactly the at-least-once
redelivery that `processed_events` absorbs.

On exit, a `finally` block stops the consumer, which leaves the consumer group cleanly and
triggers an immediate rebalance instead of waiting out the session timeout.

### The `processed_events` ledger

Every consuming service has an identical table:

| Column | Type | Purpose |
|---|---|---|
| `event_id` | UUID **PRIMARY KEY** | The `event_id` from the incoming envelope. |
| `processed_at` | TIMESTAMPTZ NOT NULL, `NOW()` | When it was handled. |

The primary key is doing real work. The application-level `SELECT 1 FROM processed_events`
is a fast path; if two consumers somehow race past it simultaneously, the second one's
`INSERT` raises a unique violation, **its entire transaction aborts, and its business
logic is undone**. The PK is the last line of defence.

**The ordering inside the transaction matters:** the ledger insert is always the *last*
statement, so an event is marked processed only if the business logic above it succeeded.

## 1.5 Request ID middleware

Runs on every HTTP request in every service.

- Reads `X-Request-ID` from the incoming headers (nginx always sets it); if absent,
  generates a fresh UUID4.
- Calls `clear_contextvars()`, then binds `request_id`. **Note the side effect:** the
  clear also wipes the globally-bound `service` name, so log lines emitted inside a
  request handler carry `request_id` but not `service`.
- Stashes the ID on `request.state.request_id` so handlers can read it.
- Starts a performance counter, awaits the route, computes `duration_ms`.
- Echoes `X-Request-ID` back in the response headers.
- Logs `request_completed` with method, path, status_code, duration_ms.

## 1.6 Health and metrics

**`GET /health`** — acquires a pooled connection and runs `SELECT 1`.
Success → `{"status":"healthy","checks":{"database":"healthy"}}` with **200**.
Any exception is caught, the error string is embedded in the check value, a
`health_check_db_failed` warning is logged, and **503** is returned.

> **It checks Postgres only.** Kafka connectivity, consumer liveness, and relay liveness
> are not covered — so this endpoint can report healthy while the saga is completely
> stalled.

**`GET /metrics`** — renders the Prometheus registry:

| Metric | Type | Labels |
|---|---|---|
| `http_requests_total` | Counter | method, endpoint, status |
| `http_request_duration_seconds` | Histogram | method, endpoint |
| `kafka_messages_consumed_total` | Counter | topic, status |
| `outbox_events_published_total` | Counter | — |

## 1.7 Graceful shutdown

On SIGTERM, FastAPI resumes each service's `lifespan` generator past the `yield`:

1. **Set the shutdown event** — one flag that every background task watches.
2. **Gather all background tasks with `return_exceptions=True`** — waits for all of them.
   The consumer finishes its current batch, commits offsets, exits its loop, and its
   `finally` stops the consumer. The relay's interruptible wait returns instantly, it
   exits its loop, and then performs **one final drain** — flushing events written by the
   very last requests before the process dies. `return_exceptions=True` ensures one task
   failing does not prevent the others from being awaited.
3. **Stop the producer** — flushes in-flight sends and closes the connection.
4. **Close the database pool** — waits for checked-out connections to return, then closes
   all of them.

**The ordering is the point:** background tasks are stopped *before* the producer and pool
they depend on are torn down. If the pool closed first, the relay's final drain would fail
against a closed pool.

# PART 2 — SERVICE 1: AUTH SERVICE

**Container:** `auth-service` · **Port:** `8001` · **Database:** `auth_db`
**Public prefix:** `/auth/` (nginx strips the prefix)

**Role in the saga: none.** This is the one service with no Kafka producer, no consumer,

## 2.1 DATABASE TABLES — `auth_db`

### `users`

| Column | Type | Constraint / Default | What it actually means |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY, `DEFAULT gen_random_uuid()` | Generated **by the database**, not the application — unlike `orders.id`, this ID is not needed before the insert, so `RETURNING id` fetches it afterwards. This value becomes the JWT `sub` claim and then `orders.user_id`. |
| `email` | VARCHAR(255) | **UNIQUE** NOT NULL | The login identifier. The UNIQUE constraint is the real duplicate-registration defence; the application-level check is only a nicer error message. |
| `password_hash` | VARCHAR(255) | NOT NULL | A **bcrypt** hash including its own embedded salt. The plaintext password is never stored, never logged, and never leaves the request handler. |
| `created_at` | TIMESTAMPTZ | NOT NULL, `DEFAULT NOW()` | |

### `refresh_tokens`

| Column | Type | Constraint / Default | What it actually means |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY, `gen_random_uuid()` | Row identity. Used to delete the exact row during rotation. |
| `user_id` | UUID | NOT NULL, **REFERENCES `users(id)` ON DELETE CASCADE** | A real foreign key — legal here because both tables live inside the same service's database. Cascade means deleting a user instantly invalidates every session they hold. |
| `token_hash` | VARCHAR(255) | NOT NULL | **SHA-256** of the refresh token, not bcrypt. |
| `expires_at` | TIMESTAMPTZ | NOT NULL | Absolute expiry, computed at issue time as now + 7 days. Checked in application code, not by a constraint. |
| `created_at` | TIMESTAMPTZ | NOT NULL, `NOW()` | |

**Indexes:** `idx_refresh_tokens_user` on `(user_id)` and `idx_refresh_tokens_hash` on
`(token_hash)`. The second one is the hot path — every `/refresh` call is a lookup by hash.

### Why SHA-256 for refresh tokens but bcrypt for passwords

This is a deliberate asymmetry, and the reason is **entropy**.

A password is low-entropy and human-chosen, so it is vulnerable to dictionary and
brute-force attack. bcrypt is intentionally **slow** and salted, which makes each guess
expensive — that cost is the entire point.

A refresh token is 64 bytes of `secrets.token_urlsafe` output — cryptographically random,
astronomically large keyspace, not guessable by dictionary attack under any budget. So
the slowness buys nothing. What it *would* cost is real: bcrypt is not searchable, so
verifying a refresh token would require pulling every candidate row and bcrypt-comparing
each one. SHA-256 is deterministic, so the hash can be computed once and used as an
**indexed equality lookup** — a single index seek instead of a table scan of bcrypt
comparisons.

> The database still never holds a usable refresh token. If `auth_db` leaked, the hashes
> are not reversible.

## 2.2 THE HTTP LAYER

### 2.2.0 Startup

The `lifespan` is the **shortest of the four services**: it creates the pool and runs
migrations, then yields. **No Kafka producer, no background tasks.** On shutdown it
closes the Redis client and then the pool.

Middleware is added in this order — and Starlette applies middleware **in reverse**, so
the last one added runs first:

1. `RateLimitMiddleware` added first → **runs second**
2. `RequestIdMiddleware` added second → **runs first**

So the effective order per request is: **request_id is bound → rate limit is checked →
route handler runs.** This ordering matters: a 429 rejection still carries a request_id in
its logs and response headers, so a rate-limited request is traceable.

### 2.2.1 Rate limiting — the fail-open design

Runs on every request, before the route.

**Step 1.** Read the client IP from `request.client.host`, falling back to the literal
string `"unknown"` if Starlette could not determine it.

> **Note:** this is the *socket* peer address, not the `X-Real-IP` header nginx sets.
> Behind the proxy every request arrives from nginx's container IP, so in the composed
> deployment the limit is effectively **global across all clients**, not per-client.

**Step 2.** Get the Redis client through a lazy singleton. On the first call it connects
and issues `PING`. If the connect or ping raises, it logs `redis_connection_failed`,
leaves the singleton as `None`, and returns `None`.

**Step 3 — the fail-open branch.** If the client is `None`, log `rate_limiting_disabled`
with `reason=redis_unavailable` and **pass the request straight through**. Rate limiting
is silently off.

**Step 4 — the sliding window counter.**
- Key is `rate_limit:<client_ip>`.
- `INCR` the key. Redis creates it at 0 and returns 1 on the first request.
- **If the returned value is exactly 1**, this is the first request of a new window →
  `EXPIRE` the key to **60 seconds**.
- **If the value exceeds 30**, log `rate_limit_exceeded` and raise **429** "Rate limit
  exceeded. Try again later."

**Step 5 — exception handling.** The `HTTPException` for 429 is caught and immediately
re-raised so it is not swallowed. **Every other exception** (a Redis timeout, a connection
drop mid-window) is caught, logged as `rate_limiting_error`, and the request proceeds.

> **This is a fixed window, not a true sliding window.** The counter resets wholesale at
> the 60-second boundary, so a client can send 30 requests at second 59 and another 30 at
> second 61 — 60 requests in two seconds. There is also a narrow race: if the process dies
> between the `INCR` and the `EXPIRE`, the key has no TTL and that IP is permanently
> blocked until the key is manually deleted.

**Why fail open rather than fail closed:** rate limiting is a *protection mechanism*, not
a business requirement. If Redis dies and the limiter fails closed, a non-critical cache
outage becomes a total authentication outage — nobody can log in, and therefore nobody can
order. Failing open means a brief window of unprotected endpoints, which is the strictly
smaller harm. In production the `rate_limiting_disabled` warning is the alerting signal.

### 2.2.2 `POST /register` → 201

**Step 1 — Pydantic validation.** `RegisterRequest` requires `email` (typed **`EmailStr`**,
so the format is validated by Pydantic before the handler runs) and `password` (plain
`str`). A malformed email → **422** automatically.

> There is **no** minimum length, complexity, or maximum-length validator on `password`.
> An empty string is structurally accepted.

**Step 2 — Hash first, query second.** `bcrypt.gensalt()` generates a fresh random salt
and `bcrypt.hashpw` produces the hash. Note this happens **before** the database is
touched — so the bcrypt cost (deliberately ~100 ms) is paid even for a request that is
about to be rejected as a duplicate. That is incidentally useful: it flattens the timing
difference between "email taken" and "email free", removing a timing side channel for
user enumeration.

**Step 3 — Existence check.** `SELECT id FROM users WHERE email = $1`. If a row comes
back → **409** "Email already registered".

**Step 4 — Insert.** `INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING
id, email, created_at`. `RETURNING` avoids a second round-trip to read back the
database-generated UUID and timestamp.

> **These two statements are *not* wrapped in a transaction.** Two simultaneous
> registrations with the same email can both pass the check in Step 3. The `UNIQUE`
> constraint on `email` then rejects the second `INSERT`, which surfaces as an unhandled
> exception → **500** rather than a clean 409. The data stays correct; only the error code
> is wrong.

**Step 5.** Log `user_registered` with user_id and email. Return **201** with
`{id, email, created_at}`. **No token is issued by registration** — the client must call
`/login` separately.

### 2.2.3 `POST /login` → 200

**Step 1.** Validate `{email, password}`.

**Step 2.** `SELECT id, email, password_hash FROM users WHERE email = $1`.

**Step 3 — Verification.** A single combined condition: if no row was found **or**
`bcrypt.checkpw` fails → **401** "Invalid email or password". The identical message and
status for both cases is intentional: it prevents an attacker from distinguishing
"this email is not registered" from "wrong password", which would otherwise let them
enumerate valid accounts.

> Python's `or` short-circuits, so when no user exists bcrypt is never called and the
> response returns measurably faster. The enumeration channel is closed at the message
> level but a timing difference remains.

**Step 4 — Build the access token.** A JWT signed with **HS256** using the shared
`JWT_SECRET`, carrying:

| Claim | Value |
|---|---|
| `sub` | the user's UUID as a string |
| `email` | the user's email |
| `exp` | now + **15 minutes** |
| `iat` | now |
| `type` | the literal `"access"` |

> **`HS256` is symmetric.** The same secret both signs and verifies, which is why
> `JWT_SECRET` must be present in *both* auth-service and order-service environments and
> why they must match exactly. The consequence: any service holding the secret can also
> *mint* tokens, not just verify them. An asymmetric algorithm (RS256) would let Auth hold
> the private key and give verifiers only the public key — a meaningful hardening step
> this project does not take.
>
> Note also that the `type: "access"` claim is written but **never checked** by the Order
> service's verification.

**Step 5 — Build the refresh token.** `secrets.token_urlsafe(64)` produces the token
returned to the client; SHA-256 of it is what goes to the database.

**Step 6 — Store the hash.** A **second, separate** pool acquisition inserts into
`refresh_tokens` with `expires_at = now + 7 days`.

> No transaction, and no reuse of the first connection. If this insert fails, the client
> receives a 500 and no tokens — consistent, if wasteful.

**Step 7.** Log `user_logged_in`. Return `{access_token, refresh_token, token_type:
"bearer"}`.

**The two-token design:** the access token is deliberately short-lived (15 min) so a
stolen one expires quickly, and it is **stateless** — Order service verifies it purely by
checking the signature, with no call back to Auth and no database lookup. That is what
lets Order stay independent. The refresh token is long-lived (7 days) but **stateful** —
it exists as a row, so it can be revoked, which the access token cannot be.

### 2.2.4 `POST /refresh` → 200 (with rotation)

**This is the only Auth endpoint that uses an explicit transaction**, and it needs one.

Hash the presented token with SHA-256, then **BEGIN**:

**Step 1 — Lookup with join.** `SELECT rt.id, rt.user_id, rt.expires_at, u.email FROM
refresh_tokens rt JOIN users u ON u.id = rt.user_id WHERE rt.token_hash = $1`. The join
pulls the email in the same round trip because the new access token needs it.

**Step 2 — Not found** → **401** "Invalid refresh token".

**Step 3 — Expired.** If `expires_at` is in the past: **delete the row** (housekeeping —
an expired token is dead weight), then raise **401** "Refresh token expired".

> The `HTTPException` propagates out of the `async with conn.transaction()` block, so
> asyncpg treats it as a failure and issues **ROLLBACK** — meaning **the delete is undone**.
> The expired row survives. The cleanup is written but never actually takes effect.

**Step 4 — ROTATION: delete the old token.** The presented refresh token is destroyed
immediately, before the new one is issued. **Single-use semantics.**

**Step 5 — Issue a new pair.** A new 15-minute access token and a brand-new 64-byte
refresh token.

**Step 6 — Insert the new hash** with a fresh 7-day expiry.

**COMMIT.** Steps 4 and 6 are in the same transaction, so it is impossible to end up
having destroyed the old token without having created the new one — the user can never be
locked out by a crash mid-rotation.

**Why rotate at all:** without rotation, a stolen refresh token is usable for its full
7-day life alongside the legitimate one, undetectably. With rotation, each token works
exactly once. If an attacker uses a stolen token first, the legitimate user's next refresh
fails with 401 — a visible signal that something is wrong. (This design detects theft; it
does not yet *react* to it. A full reuse-detection scheme would keep the consumed token
and revoke the entire token family on replay.)

Standard — see §1.6. Auth's `/health` checks Postgres only; **Redis is not checked**,
which is consistent with the fail-open stance: a dead Redis is not an unhealthy service.

## 2.5 ANYTHING ELSE — Redis lifecycle

A module-level singleton holds the client, created lazily on first use. On shutdown the
`lifespan` closes it and resets the singleton to `None`.

> **Failure recovery is asymmetric.** If the very first connection attempt fails, the
> singleton stays `None` and *every subsequent request retries the connection* — so Redis
> coming up late is handled. But if Redis dies *after* a successful connect, the singleton
> still holds a now-broken client. Every request then takes the try/except fail-open path
> in Step 5 of §2.2.1 — the service keeps working, but it never reconnects, so rate
> limiting stays off until the process restarts.

## 3.2 THE HTTP LAYER

### 3.2.0 Startup sequence

The `lifespan` runs, in this exact order:

1. `setup_logging("order-service")`.
2. Create the pool against `order_db`, register the JSONB codec, run migrations
   (`001_init.sql` then `002_idempotency_key.sql` — lexical order).
3. Create and start the Kafka producer.
4. Create a single `asyncio.Event` named `shutdown_event`.
5. **Spawn two background asyncio tasks** onto the same event loop as the HTTP server:
   the consumer loop and the outbox relay. Both receive the same `shutdown_event`.
6. `yield` — the app now serves traffic.

Then `RequestIdMiddleware` is attached (Order has **no** rate limiter), followed by the
order routes, the `/health` router, and the `/metrics` route.

### 3.2.1 `POST /orders` → **202 Accepted**

> **202, not 201.** This is the central design statement of the whole system: the resource
> is *accepted for processing*, not created-and-final. The order exists in `PENDING`;
> whether it becomes a real order is decided asynchronously, seconds later, by two other
> services.

**Step 1 — Authentication (dependency, runs before the handler body).**

Reads the `Authorization` header. If missing, or not prefixed with `Bearer ` → **401**
"Missing or invalid authorization header". Otherwise split on the first space and decode
the token with the shared `JWT_SECRET` and `HS256`. Three distinct outcomes:

- expired signature → **401** "Token expired"
- any other invalid token (bad signature, malformed, wrong algorithm) → **401** "Invalid
  token"
- success → returns `{user_id: <sub>, email: <email>}`

> Verification is **entirely local** — no network call to Auth, no database lookup. That
> statelessness is why Order can serve traffic even if Auth is completely down.
>
> Two things are notably *not* checked: the `type: "access"` claim, so a token of any type
> signed with the same secret is accepted; and any revocation list, so a stolen access
> token remains valid for its full 15 minutes with no way to kill it.

**Step 2 — Body validation (Pydantic).** `CreateOrderRequest` requires `restaurant_id`
(UUID) and `items` (a list of `{item_id: UUID, quantity: int, price: float}`). Any type
mismatch → **422** before the handler body runs.

> There is **no** `quantity > 0` or `price >= 0` validator, and no non-empty check on
> `items`. A negative quantity is structurally accepted here and would produce a negative
> `total_amount` and, downstream, a stock *increase*.

**Step 3 — Header capture.** `X-Payment-Simulate` and `Idempotency-Key` are pulled as
optional headers.

**Step 4 — Idempotency fast path.**

*Only if* `Idempotency-Key` was supplied: acquire a connection and
`SELECT id, status FROM orders WHERE idempotency_key = $1 AND user_id = $2`.

Scoping by `user_id` means one user's key can never surface another user's order.

- **Row found** → return immediately with that order's real `id` and its **current**
  status, plus the message `"Order already accepted (Idempotent response)"`. No new order,
  no new event. A client retrying after a network timeout gets the original order back.
- **No row** → fall through.

> This read happens **outside** the write transaction, so two genuinely simultaneous
> requests carrying the same key both pass this check. The `UNIQUE` constraint in Step 8
> is what actually stops the second one — by raising a unique violation that surfaces as a
> **500** rather than a clean idempotent 202.

**Step 5 — Generate the order ID.** A UUID4 is minted **in application code**, not by the
database default. This is essential: the ID must be known *before* the INSERT, because the
same ID has to go into the event payload and the Kafka key inside the same transaction.

**Step 6 — Normalize items and compute the total.** Each item is flattened to a plain dict
with `item_id` stringified. `total_amount` is the sum of quantity × price.

> The arithmetic is server-side, but the **prices are client-supplied**. The order total is
> whatever the client says the items cost — restaurant service checks stock but never
> re-validates price against `menu_items.price`. This is the single largest trust gap in
> the system.

**Step 7 — Build the event envelope.** An inner payload is assembled with `order_id`,
`user_id`, `restaurant_id`, `items`, `total_amount`. If `X-Payment-Simulate` was present,
`payment_simulate` is added — this is how a test directive propagates across three service
boundaries. Then the wrap helper adds a fresh UUID4 `event_id`, the `event_type`
`order.placed`, and an ISO-8601 UTC `occurred_at`.

> **The `event_id` generated here is the exact value that restaurant-service will write
> into its own `processed_events` table.**

**Step 8 — THE TRANSACTIONAL OUTBOX WRITE.**

A connection is acquired and **BEGIN** is issued. Inside this transaction, exactly two
statements run:

> **(a)** `INSERT INTO orders` — id, user_id, restaurant_id, items, total_amount,
> `status='PENDING'` (a **hardcoded literal in the SQL**, not a parameter — the caller
> cannot choose a starting state), payment_simulate, idempotency_key.
>
> **(b)** `INSERT INTO outbox_events` — `topic='order.placed'`, `key=<order_id as string>`,
> `payload=<the envelope>`, `created_at=NOW()`.

Then **COMMIT**.

**This is the single most important mechanism in the system.** See §1.2 for the full
reasoning. In this specific case: the order row and the "tell the world about this order"
intent land together or not at all. If the transaction fails for any reason — constraint
violation, connection loss — asyncpg's transaction context manager issues **ROLLBACK**:
no order row, no outbox row, no event. The client gets a 500 and can safely retry.

**Step 9 — Log and respond.** Logs `order_created` with order_id, user_id, total_amount.
Returns **202** with `{id, status: "PENDING", message: "Order accepted for processing"}`.

> **At this instant the order's fate is completely undetermined.** No stock has been
> checked. No payment has been attempted. The event is not even in Kafka yet — it is
> sitting in a Postgres table waiting for the relay to notice it, up to one second later.

### 3.2.2 `GET /orders/{order_id}` — saga status polling

The same JWT dependency runs first. The path parameter is coerced to UUID by FastAPI, so a
malformed ID → **422**.

- `SELECT * FROM orders WHERE id = $1` — a plain read: no lock, no transaction.
- No row → **404** "Order not found".
- **Ownership is checked in application code, after the fetch:** the row's `user_id` is
  stringified and compared to the JWT's `user_id`. Mismatch → **403** "Access denied".

  > The row is read from the database *before* authorization is evaluated. The data is
  > fetched but never returned — correct behaviour, slightly wasteful shape.

- Serialized into the response model: UUIDs stringified, `total_amount` cast from DECIMAL
  to float, timestamps rendered as ISO-8601.

This is the endpoint the client polls to watch the saga resolve: `PENDING` → then
eventually `CONFIRMED`, `PAYMENT_FAILED`, or `STOCK_UNAVAILABLE`.

## 3.4 THE BACKGROUND CONSUMER

**Subscribes to:** `payment.succeeded`, `payment.failed`, `stock.rejected`
**Consumer group:** `order-service`

The loop shape is the standard one from §1.4. Order's consumer is the only one that also
logs the **Kafka offset** on error, which makes a failed message locatable in the topic.

### The message handler — one event, one transaction

Unwrap the envelope into `event_id` (converted to UUID), `event_type`, and `payload`.

Acquire a connection, **BEGIN**. Everything below happens inside this one transaction —
the idempotency check, the state change, the compensation write, and the ledger insert.
**This is the property that makes the consumer safe.**

**Step A — Idempotency check.** `SELECT 1 FROM processed_events WHERE event_id = $1`. If a
row exists, log `duplicate_event_skipped` and **return**. The `return` exits the
transaction context manager normally, so the transaction commits having done nothing. A
redelivered event is a clean no-op.

**Step B — Extract `order_id`** from the payload. This is the saga correlation key.

**Step C — Branch on `event_type`:**

---

#### CASE `payment.succeeded` → SAGA COMPLETES SUCCESSFULLY

Transition the order to **`CONFIRMED`**. Nothing else happens.

This is the happy-path terminus: stock is already reserved (restaurant service did that),
money is already captured (payment service did that), and the order is now a real order.

---

#### CASE `payment.failed` → SAGA COMPENSATES

Two things happen, **atomically, in the same transaction**:

1. Transition the order to **`PAYMENT_FAILED`**.
2. Build a `stock.release` envelope (fresh `event_id`, fresh timestamp, payload
   `{order_id}`) and **INSERT it into `outbox_events`** with `topic='stock.release'` and
   `key=<order_id>`.

**This is the compensating transaction of the saga, and this is where the pattern earns
its keep.**

In a monolith with one database, a failed payment would simply `ROLLBACK` and the stock
decrement would vanish with it. Here, the stock reservation lives in `restaurant_db` — a
**different database, inside a different service** — and it was **already committed**,
seconds ago, by a different process. There is no rollback available. Postgres cannot undo
a committed transaction in another database it has never heard of.

The only way to undo it is to perform a **new, forward-moving transaction that
semantically reverses the effect**: put the stock back. That is what a compensating
transaction *is* — not a rollback, but a deliberate inverse operation, issued as a normal
business event.

**And note where the compensation is written: the outbox, not Kafka.** The same reasoning
as §1.2 applies here with even more force. If the order were marked `PAYMENT_FAILED` in
the database but the `stock.release` publish then failed, the reservation would be
**orphaned forever** — inventory permanently consumed by an order that was never paid for,
with nothing in the system that would ever notice. Because the status update and the
compensation event are in one transaction, "this order failed" and "the stock will be
released" become the same durable fact. The relay then guarantees eventual delivery.

**Failure atomicity, concretely:** if the transition raises `InvalidTransitionError` —
because this order was already `CONFIRMED`, say — the whole transaction rolls back: no
status change, **no `stock.release` outbox row**, and no `processed_events` entry. The
system cannot end up in the state "compensation queued for an order that was never marked
failed."

---

#### CASE `stock.rejected` → SAGA ABORTS EARLY

Transition the order to **`STOCK_UNAVAILABLE`**.

**No compensation is emitted, and that is correct.** This event means the restaurant
service *refused* to reserve, so nothing was ever decremented and no side effect exists to
undo. Payment was never attempted; the payment service never even saw this order. This is
the cheapest failure path in the saga — it terminates at step one, with nothing to unwind.

---

#### DEFAULT — unknown event type

Log `unknown_event_type` at warning level and return. The `processed_events` insert is
**skipped**, so an unknown event is not recorded as processed — but the Kafka offset still
advances with the batch commit, so it is not retried either.

---

**Step D — Record in the ledger.** `INSERT INTO processed_events (event_id) VALUES ($1)`,
in the same transaction. **The position matters:** the ledger insert is the *last*
statement, so the event is only marked processed if the business logic above it succeeded.
And because `event_id` is the PRIMARY KEY, if two consumer instances somehow raced past
the Step A check simultaneously, one of them hits a unique violation here, its entire
transaction aborts, and its business logic is undone.

**COMMIT.** Then, outside the transaction, log `event_processed`.

---

## 3.5 ANYTHING ELSE — the order state machine

Called only from inside an already-open transaction. It performs three things.

**Step 1 — Lock the row.**

> `SELECT status FROM orders WHERE id = $1 FOR UPDATE`

**`FOR UPDATE` takes a row-level exclusive lock held until the enclosing transaction
commits.** Any concurrent transaction attempting to transition the same order **blocks
here** until the first one finishes, then re-reads the *committed* status.

This closes the read-modify-write race. Without the lock, two events arriving
simultaneously could both read `PENDING`, both judge their transition legal, and both
write — last-write-wins, silently, with no error. With it, the second transaction reads
the *already-updated* status and its transition is correctly rejected.

**Step 2 — Two guards.**

- If the status is `NULL` (no such order) → raise `ValueError`. This bubbles up, the
  transaction rolls back, and the consumer's try/except logs it while the batch continues.
- Look up the current status in the transition whitelist. The table has **exactly one
  entry**:

| From | Allowed to |
|---|---|
| `PENDING` | `CONFIRMED`, `PAYMENT_FAILED`, `STOCK_UNAVAILABLE` |

  **The three terminal states are deliberately absent from the table.** The lookup uses a
  default of the empty set, so *every* transition out of a terminal state is rejected with
  `InvalidTransitionError`.

**Step 3 — Write.**

> `UPDATE orders SET status = $1, updated_at = NOW() WHERE id = $2`

Then log `order_transitioned` with the from- and to-status.

### Why the whitelist is the saga's safety net

Kafka is at-least-once, and its ordering guarantee holds only *within* a partition. If a
delayed or duplicated `payment.succeeded` arrives after the order has already gone to
`PAYMENT_FAILED`, the state machine refuses it — **an order cannot be resurrected into
`CONFIRMED` after its compensation has already fired and the stock has been given back.**

Note that this is a *different* defence from the ledger:

| Mechanism | Catches |
|---|---|
| `processed_events` (PK on `event_id`) | The **exact same event** delivered twice. |
| The transition whitelist (+ `FOR UPDATE`) | **Different events that semantically conflict** — distinct `event_id`s that would drive the order into an illegal state. |

Two independent defences against two genuinely different failure modes. Neither subsumes
the other.

## 3.6 ORDER SERVICE'S POSITION IN THE SAGA

| # | Direction | Event | Counterparty | Order-side effect |
|---|---|---|---|---|
| 1 | **OUT** | `order.placed` | → restaurant-service | Starts the saga. Order is `PENDING`. |
| 2 | **IN** | `stock.rejected` | ← restaurant-service | → `STOCK_UNAVAILABLE`. Terminal. No compensation needed. |
| 3 | **IN** | `payment.succeeded` | ← payment-service | → `CONFIRMED`. Terminal. Saga complete. |
| 4 | **IN** | `payment.failed` | ← payment-service | → `PAYMENT_FAILED` **and emits `stock.release`**. |
| 5 | **OUT** | `stock.release` | → restaurant-service | The compensating transaction. |

Order service **never** talks to restaurant or payment over HTTP. Every interaction is an
event through Kafka, and every event it emits is written to its own database first. It has
no knowledge of *how* stock is reserved or *how* payment is captured — only that outcome
events will eventually arrive.

# PART 4 — SERVICE 3: RESTAURANT SERVICE

**Container:** `restaurant-service` · **Port:** `8003` · **Database:** `restaurant_db`
**Public prefix:** `/restaurants` (prefix preserved)

**Role in the saga:** Restaurant Service is the **first saga participant** and the only
one that performs a **reversible** side effect. It reserves stock on `order.placed`, and
it is the target of the compensation on `stock.release`. It is the reason the saga pattern
is needed at all — its stock decrement is committed in its own database long before anyone
knows whether the payment will succeed.

It is also the only service whose HTTP layer and whose saga participation are almost
completely disconnected: the REST endpoints are read-only browsing, and every write comes
from Kafka.

| Column | Type | Constraint / Default | What it actually means |
|---|---|---|---|
| `item_id` | UUID | **PRIMARY KEY**, REFERENCES `menu_items(id)` ON DELETE CASCADE | The PK *is* the FK — a strict one-row-per-item relationship, so there is exactly one stock row to lock per item. |

> were ever bypassed or raced, the constraint aborts the transaction rather than allowing
> a negative stock level. It is the same defence-in-depth pattern as the `event_id`
> primary key: an application-level check for a good error message, a database constraint
> for actual correctness.

### `stock_reservations` — the compensation record

| Column | Type | Constraint / Default | What it actually means |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY, `gen_random_uuid()` | Row identity. |
| `order_id` | UUID | NOT NULL **UNIQUE** | The saga correlation ID. **The UNIQUE constraint is a second, independent idempotency guard** — see §4.4. |
| `items` | JSONB | NOT NULL | A **snapshot of exactly what was deducted**, stored so the release knows precisely what to give back. |
| `created_at` | TIMESTAMPTZ | NOT NULL, `NOW()` | |

**Why this table exists at all.** The compensation event carries only `{order_id}` — it
does not carry the items. Order service does not know or care what was deducted; that is
restaurant service's private business. So restaurant service must remember, itself, what
it took, in order to know what to give back later. This table *is* that memory.

It is also **self-deleting**: on release, the row is removed after the quantities are
restored, which means the reservation table only ever holds *outstanding* reservations.
That has a useful property — a row here for an order that is already `CONFIRMED` is
normal, but a row here for an order that is `PAYMENT_FAILED` means the compensation has
not landed yet.

Standard shapes — see §1.2 and §1.4. Restaurant writes two topics into the outbox:

## 4.2 THE HTTP LAYER

### 4.2.0 Startup

Identical in shape to Order (§3.2.0): pool + migrations → Kafka producer → shutdown event

### 4.2.1 `GET /restaurants` → 200

**No JWT required.** Browsing is public.

`SELECT id, name, description FROM restaurants ORDER BY name` — a plain read, no
transaction, no lock, no pagination. Returns a list of `{id, name, description}` with the
UUID stringified.

> No `LIMIT` and no cursor. With two seeded rows this is fine; at scale it returns the
> entire table on every call.

### 4.2.2 `GET /restaurants/{restaurant_id}/menu` → 200

Path parameter coerced to UUID by FastAPI → malformed gives **422**.

**Step 1 — Existence check.** `SELECT 1 FROM restaurants WHERE id = $1`. No row → **404**
"Restaurant not found". This is a separate round-trip done deliberately, so that "this
restaurant does not exist" (404) is distinguishable from "this restaurant exists but has
no menu items" (an empty 200 list) — a plain join could not tell those apart.

**Step 2 — Fetch the menu with stock.**

> `SELECT m.id, m.name, m.description, m.price, s.quantity FROM menu_items m LEFT JOIN menu_item_stock s ON s.item_id = m.id WHERE m.restaurant_id = $1 ORDER BY m.name`

**`LEFT JOIN`, not an inner join** — a menu item that has never had a stock row still
appears in the menu, with a NULL quantity. The application then coalesces that NULL to
**0** in the response. An inner join would silently hide such items from the menu
entirely, which is the wrong failure mode: the customer should see the dish and see it as
unavailable, not find that it vanished.

**Step 3 — Serialize.** `price` cast DECIMAL → float; `quantity` exposed as
`stock_quantity`.

> **Both endpoints read stock without any lock.** The `stock_quantity` shown is a snapshot
> that may already be stale by the time the response reaches the browser — another order's
> saga may be mid-reservation. This is correct and intentional: browsing must not take
> locks on the contended resource, or every page view would contend with every order. The
> authoritative check happens under `FOR UPDATE` at reservation time (§4.4).

### 4.2.3 Health and metrics

Standard — see §1.6.

> **There is no HTTP endpoint that reserves or releases stock.** Every mutation of
> `menu_item_stock` arrives through Kafka. The REST surface is strictly read-only.

## 4.4 THE BACKGROUND CONSUMER — the most intricate handler in the system

**Subscribes to:** `order.placed`, `stock.release`
**Consumer group:** `restaurant-service`

Standard loop shape (§1.4). The handler, however, has **three nested layers of failure
handling**, and each layer exists for a different reason.

### The layered structure

```
outer try                        ← catches UniqueViolation on stock_reservations
  BEGIN (outer transaction)      ← idempotency + outbox + ledger
    inner try                    ← catches InsufficientStockError
      SAVEPOINT (nested txn)     ← isolates the stock deductions
        reserve_stock(...)
      RELEASE SAVEPOINT
    except InsufficientStockError:
      write stock.rejected outbox row
  COMMIT
except UniqueViolationError:
  swallow if it is the reservation key
```

### Step A — Idempotency check

Inside the outer transaction: `SELECT 1 FROM processed_events WHERE event_id = $1`. Row
found → log `duplicate_event_skipped` and return, committing an empty transaction.

### Step B — Extract `order_id`.

### Step C — Branch on `event_type`

---

#### CASE `order.placed` → THE FORWARD SAGA STEP

**C.1 — Open a SAVEPOINT.** A nested transaction is opened *inside* the outer one. In
Postgres this is a `SAVEPOINT`, not a second transaction — it can be rolled back
independently while the outer transaction stays alive.

**C.2 — Attempt the reservation.** Inside the savepoint, for **each item in the order, in
order**:

1. > `SELECT quantity FROM menu_item_stock WHERE item_id = $1 FOR UPDATE`
   >
   > **`FOR UPDATE` locks that item's stock row for the rest of the transaction.** This is
   > the concurrency control for the entire system's most contended resource. Two orders
   > for the same item arriving at the same instant **serialize here**: the second one
   > blocks on the lock until the first commits or rolls back, then re-reads the
   > *committed* quantity. Without this lock, both would read the same starting quantity,
   > both would judge themselves satisfiable, and both would deduct — overselling the item.

2. **If the row is NULL** (no stock row → the item does not exist) → raise
   `InsufficientStockError` with "Item not found". **This is how an order for a
   nonexistent menu item is rejected**, and it is why Order service can safely skip
   validating `restaurant_id` and `item_id` at HTTP time.

3. **If `quantity < requested`** → raise `InsufficientStockError` with the requested and
   available amounts, which is carried into the rejection event as a human-readable
   `reason`.

4. Otherwise > `UPDATE menu_item_stock SET quantity = quantity - $1 WHERE item_id = $2`
   >
   > Note this is a **relative** update (`quantity - N`), not an absolute one
   > (`SET quantity = <value read earlier>`). Combined with the `FOR UPDATE` lock this is
   > belt-and-braces, but the relative form is correct regardless of what any concurrent
   > transaction did.

**C.3 — Record the reservation.** After every item has been deducted:
`INSERT INTO stock_reservations (order_id, items) VALUES ($1, $2)` — storing the exact
items list so the compensation knows what to restore. Log `stock_reserved`.

**C.4 — On success**, back in the outer transaction: build a `stock.reserved` envelope
**wrapping the entire original payload** — including `total_amount` and, crucially,
`payment_simulate` — and insert it into `outbox_events` with `key=<order_id>`.

> **This forwarding of the whole payload is what carries the order total to the payment
> service.** Payment service has no database access to `order_db` and no HTTP call to
> Order; the only way it can learn what to charge is because restaurant service copies the
> amount forward. The `payment_simulate` directive rides along the same way.

---

**C.5 — THE PARTIAL-ROLLBACK MECHANISM.** This is the subtlest piece of the codebase.

Consider a two-item order: item A has plenty of stock, item B has none.

- Item A is locked, checked, and **deducted**. That `UPDATE` has really happened inside
  the transaction.
- Item B is locked, checked, and **raises**.

Without the savepoint, item A's deduction would be part of the same flat transaction as
everything else. To write the `stock.rejected` event you must commit that transaction —
and committing it would **also commit item A's deduction**, permanently losing that stock
to an order that was rejected and will never be released (there is no
`stock_reservations` row for it, so a later `stock.release` would find nothing).

The savepoint solves this precisely:

- The `InsufficientStockError` escapes the nested transaction block, so **the savepoint
  rolls back** — item A's deduction is undone, item B was never deducted, and the
  `stock_reservations` insert never ran.
- **The outer transaction survives.** It is still open and still usable, which is what
  allows the rejection to be recorded in the very next step.

> **The `except` clause MUST sit outside the savepoint block, and the code says so
> explicitly.** If the `InsufficientStockError` were caught *inside* the nested block, the
> savepoint's context manager would never see an exception, would treat the block as
> successful, and would **release** the savepoint rather than rolling it back — committing
> the partial deductions. Moving the `except` two lines in would silently reintroduce the
> exact bug the savepoint exists to prevent.

**C.6 — On `InsufficientStockError`:** log `stock_reservation_failed` with the reason, then
insert a `stock.rejected` envelope — payload `{order_id, reason}` — into `outbox_events`
with `key=<order_id>`.

> Note the rejection payload is **minimal**: only the order ID and a reason string. It does
> not forward the items or the amount, because the only consumer is Order service and all
> it needs to do is set a terminal status.

---

#### CASE `stock.release` → THE COMPENSATION

The compensating handler, invoked when Order service reports that payment failed.

1. > `SELECT items FROM stock_reservations WHERE order_id = $1`

2. **If no row is found**: log `stock_release_not_found` at warning level and **return
   without raising.**

   > This is deliberate and it is the correct behaviour. Reaching here means either the
   > reservation never happened (so there is nothing to give back), or a duplicate
   > `stock.release` arrived after the first one already deleted the row. Treating a
   > missing reservation as an error would turn a benign duplicate into a permanently
   > failing message. **Making the release a no-op when there is nothing to release is
   > what makes the compensation idempotent at the business level**, independently of the
   > `processed_events` ledger.

3. **For each item in the stored snapshot:**
   > `UPDATE menu_item_stock SET quantity = quantity + $1 WHERE item_id = $2`
   >
   > **Note what is absent: there is no `SELECT … FOR UPDATE` here.** The reservation path
   > locks because it must *read-then-decide*; the release path only ever *adds*, and a
   > relative `+ N` update takes its own row lock implicitly and is safe to interleave with
   > any other addition or subtraction. Two concurrent releases cannot lose an increment.
   > The asymmetry is correct, not an oversight: locking is needed for the conditional
   > deduct, not for the unconditional restore.

4. **Delete the reservation row.** This is what makes a *second* delivery of the same
   `stock.release` find nothing in step 2 and no-op cleanly.

5. Log `stock_released`.

---

#### DEFAULT — unknown event type

Log `unknown_event_type` and return without writing to the ledger.

### Step D — Record in the ledger

`INSERT INTO processed_events (event_id) VALUES ($1)` — last statement in the outer
transaction, same reasoning as §1.4.

### The outer `except` — the fourth idempotency layer

The outer try/except catches `UniqueViolationError` and inspects the message:

- **If it names `stock_reservations_order_id_key`**, log `duplicate_reservation_skipped`
  and **swallow it**. This means: an `order.placed` event arrived whose `event_id` was
  *not* in `processed_events`, but whose `order_id` already had a reservation. That can
  happen if the ledger write was lost while the reservation committed, or if the same
  order were somehow re-published with a fresh `event_id`. The stock has already been
  deducted exactly once; deducting again would be the actual bug, and the UNIQUE constraint
  prevents it. Swallowing the error means the message is not retried forever.
- **Any other unique violation is re-raised** and handled by the consumer loop's generic
  error path.

> **Restaurant service therefore has three independent idempotency mechanisms** guarding
> the same operation, keyed on different things:
>
> | Mechanism | Keyed on | Catches |
> |---|---|---|
> | `processed_events` PK | `event_id` | The exact same event delivered twice. |
> | `stock_reservations.order_id` UNIQUE | `order_id` | Any second reservation for one order, whatever its event_id. |
> | Empty-result no-op on release | `order_id` | A repeated compensation after the row is gone. |

---

## 4.5 ANYTHING ELSE — why stock is the reason the saga exists

Restaurant service's deduction is the **only irreversible-by-rollback side effect in the
forward path**, and every architectural decision in this system flows from that one fact:

- It commits in `restaurant_db` before anyone knows the payment outcome, so it must be
  undoable by a *forward* operation rather than a rollback → **`stock.release` exists**.
- Undoing it requires knowing what was taken, and the compensating event carries only an
  order ID → **`stock_reservations` exists**.
- Multiple orders contend for the same rows → **`SELECT … FOR UPDATE` exists**.
- A multi-item order can fail halfway through its own deductions → **the savepoint
  exists**.
- Redelivery must not double-deduct → **three idempotency layers exist**.

# PART 5 — SERVICE 4: PAYMENT SERVICE

**Container:** `payment-service` · **Port:** `8004` · **Database:** `payment_db`
**Public prefix:** `/payments` (prefix preserved)

**Role in the saga:** Payment Service is the **final saga participant** and the one that
decides the outcome. It is the only service with **three** background tasks instead of two,
and the only one that deliberately **breaks the one-transaction-per-message rule** — for a
reason that is central to how distributed payment systems have to work.

## 5.1 DATABASE TABLES — `payment_db`

### `payments`

| Column | Type | Constraint / Default | What it actually means |
|---|---|---|---|
| `id` | UUID | PRIMARY KEY, `gen_random_uuid()` | Payment identity. In a real system this is what you would present to the provider to look a charge up. |
| `order_id` | UUID | NOT NULL **UNIQUE** | The saga correlation ID. **The UNIQUE constraint is the hard guarantee that one order can be charged at most once**, independent of the event ledger. |
| `amount` | DECIMAL(10,2) | NOT NULL | Copied from `total_amount` on the incoming `stock.reserved` payload. |
| `status` | VARCHAR(50) | NOT NULL | `PROCESSING` → `SUCCEEDED` or `FAILED`. Note: no default — the insert always states it explicitly. |
| `payment_simulate` | VARCHAR(20) | nullable | Added by migration `002`. **Persisting this is what makes crash recovery correct** — see §5.5. |
| `created_at` | TIMESTAMPTZ | NOT NULL, `NOW()` | |

### `outbox_events` and `processed_events`

Standard shapes — see §1.2 and §1.4. Payment writes `payment.succeeded` and
`payment.failed`.

### What migration `002` fixed

The `payment_simulate` column was added later, and the migration file documents the exact
bug it closes. The directive arrives on the `stock.reserved` event but was previously only
held **in memory** during consumption. If the service died between Transaction 1 and
Transaction 2, the reconciliation worker had no way to recover it and fell back to the
`PAYMENT_SIMULATE_DEFAULT` environment variable — which is `"success"`. So an order that
was explicitly meant to fail would be **silently reconciled to SUCCEEDED**, and the whole
compensation branch of the saga would never fire.

Storing the directive in Transaction 1 makes the outcome **recoverable from database state
alone**, which is the property the reconciliation worker depends on.

## 5.4 THE BACKGROUND CONSUMER — the two-transaction payment flow

**Subscribes to:** `stock.reserved`
**Consumer group:** `payment-service`

Standard loop shape (§1.4). The handler, however, is structured **completely differently
from Order's and Restaurant's** — and the difference is the most important design decision
in the service.

### Extraction

From the envelope: `event_id`, and from the payload `order_id`, `amount`
(the `total_amount` that restaurant service forwarded), and `payment_simulate` (read with
a `.get()`, since it is only present when the header was supplied).

---

### TRANSACTION 1 — record the intent

Acquire a connection, **BEGIN**:

**1.1 — Idempotency check.** `SELECT 1 FROM processed_events WHERE event_id = $1`. Row
found → log `duplicate_event_skipped` and **return**.

**1.2 — Insert the payment as `PROCESSING`.**

> `INSERT INTO payments (order_id, amount, status, payment_simulate) VALUES ($1, $2, 'PROCESSING', $3) RETURNING id`

`'PROCESSING'` is a hardcoded literal. `RETURNING id` captures the generated payment ID for
Transaction 2. The `payment_simulate` directive is persisted here, and only here.

**1.3 — Mark the event processed *immediately*.**
`INSERT INTO processed_events (event_id) VALUES ($1)`.

> **This is the opposite ordering from every other consumer in the system.** Order and
> Restaurant write the ledger *last*, so that a failure undoes everything. Payment writes
> it *before the work is done*, deliberately: it must be impossible for this event to be
> replayed after the gateway has been called. See below.

**COMMIT.**

**1.4 — The unique-violation catch.** If the insert raises `UniqueViolationError` naming
`payments_order_id_key`, log `duplicate_payment_skipped` and **return**. This is the
`order_id`-keyed guard: an event with a *new* `event_id` for an order that already has a
payment row cannot create a second charge. Any other unique violation is re-raised.

---

### THE GATEWAY CALL — outside any transaction

Log `calling_payment_gateway`, then invoke the gateway simulator.

**The gateway is a pure function with no randomness.** It takes the directive, falling back
to the `PAYMENT_SIMULATE_DEFAULT` environment variable (`"success"` in compose) when the
directive is absent. If the resolved directive lowercases to `"failure"` it returns false;
**everything else returns true**.

> The determinism is the entire point. `X-Payment-Simulate: failure` on the original HTTP
> request travels: header → `orders.payment_simulate` → `order.placed` payload →
> `stock.reserved` payload → `payments.payment_simulate` → gateway. This lets an
> integration test drive the **real** compensation path end-to-end through all four
> services with no mocks and no flakiness.

---

### TRANSACTION 2 — record the outcome and publish

Compute the outcome: status becomes `SUCCEEDED` or `FAILED`, topic becomes
`payment.succeeded` or `payment.failed`, and an envelope is built with payload
`{order_id}` only.

Acquire a **new** connection, **BEGIN**:

**2.1** `UPDATE payments SET status = $1, updated_at = NOW() WHERE id = $2`.

**2.2** `INSERT INTO outbox_events` with the outcome topic, `key=<order_id>`, and the
envelope.

**COMMIT.** Log `payment_completed`.

---

### WHY TWO TRANSACTIONS — the core reasoning

Every other consumer does its work in one transaction. Payment cannot, and the reason is
the **external call**.

Suppose it were one transaction: `BEGIN` → insert payment → **call the gateway** → update
status → write outbox → `COMMIT`. Two problems, both severe:

1. **You would hold a database transaction open across a network call to a third party.**
   A slow gateway means a long-held connection and long-held locks. A gateway that hangs
   for 30 seconds exhausts the pool and takes the whole service down.

2. **Far worse — a crash mid-call rolls back the record that you tried.** The transaction
   is undone, so there is no `payments` row at all. But **the gateway may have already
   charged the customer.** You now have no record whatsoever of a real charge. That is
   money moved with nothing in your database that knows about it, and no way to find it.

The two-transaction split makes that impossible:

> **Transaction 1 commits the intent to charge *before* the charge is attempted.**

So the `PROCESSING` row exists on disk before any money can move. If the process dies at
any point around the gateway call, the row survives and says, unambiguously: *we were
about to charge this order and we do not know what happened.*

That is a **known-unknown**, and a known-unknown is recoverable — you can go look it up.
The single-transaction design produces an **unknown-unknown**, which is not recoverable by
anything.

### Why the ledger write moves into Transaction 1

Writing `processed_events` in Transaction 1 rather than at the end is what prevents the
recovery from turning into a double charge.

If the ledger entry were written only in Transaction 2, then a crash after the gateway call
would leave the event **unprocessed** in the ledger. On restart, if the Kafka offset had
not been committed, the same `stock.reserved` would be redelivered, the idempotency check
would pass, and the gateway would be **called a second time** — charging the customer
twice.

By writing it in Transaction 1, the event is permanently marked as handled the instant the
intent is recorded. A redelivery short-circuits at step 1.1. The gateway is called **at most
once per event**, ever.

> **The trade-off is explicit and accepted:** the system now prefers "possibly never
> completed" over "possibly charged twice." An interrupted payment cannot be recovered by
> Kafka replay — the ledger blocks it and the offset commit blocks it. **Which is exactly
> why the reconciliation worker has to exist.**

---

## 5.5 ANYTHING ELSE — the reconciliation worker

The third background task, and the only component in the system that recovers state
**from the database rather than from Kafka**.

### The gap it fills

After the two-transaction split, exactly one failure mode remains open: **Transaction 1
committed, Transaction 2 never ran.** The service died around the gateway call.

Nothing else in the system can fix this:

- **Kafka cannot.** The offset is committed either way once the batch completes, and even
  if the message were redelivered, `processed_events` already contains the `event_id` from
  Transaction 1 — so it would short-circuit and do nothing.
- **The outbox relay cannot.** No outbox row was ever written, because that only happens in
  Transaction 2. There is nothing pending for the relay to find.
- **Order service cannot.** It is sitting in `PENDING` waiting for an event that will never
  arrive, and it has no timeout of its own.

The payment is stranded, the stock stays reserved forever, and the customer's order never
resolves. **Database state is the only remaining signal**, which is precisely what this
worker polls for.

### The worker loop

`while not shutdown_event.is_set():`

- Run one reconciliation pass.
- Catch and log **any** exception as `reconciliation_worker_error` — the loop must never
  die.
- Then the same **interruptible wait** pattern as the relay, but with a **60-second**
  interval instead of one second. Shutdown still returns immediately.

### One reconciliation pass

**Step 1 — Find stuck payments.**

> `SELECT id, order_id, amount, payment_simulate FROM payments WHERE status = 'PROCESSING' AND updated_at < NOW() - INTERVAL '3 minutes'`

Two conditions, both necessary:

- **`status = 'PROCESSING'`** — the row is in the uncertain state.
- **`updated_at` older than 3 minutes** — the **grace period**. Without it, the worker
  would grab payments that are merely *in flight right now*, between Transaction 1 and
  Transaction 2, and resolve them concurrently with the consumer that is still working on
  them. Three minutes is far longer than a normal gateway round trip, so anything older
  than that is genuinely abandoned rather than merely slow.

> The interval is interpolated into the SQL string rather than passed as a parameter — safe
> here because it is a function default (`"3 minutes"`) or a test-supplied constant, never
> user input, but it is string interpolation into SQL nonetheless.

**Step 2 — Re-derive the outcome.** For each stuck row, call the **same gateway function**
with the `payment_simulate` directive **that was persisted in Transaction 1**.

This is the payoff of migration `002`. Because the simulated gateway is a pure function of
that directive, re-deriving the answer is **exactly equivalent to asking the gateway what
it decided originally**. A payment that was meant to fail resolves to `FAILED`, not to the
environment default of success.

> **The docstring is explicit that a real system would not do this**, and the distinction
> matters. A real gateway's outcome is *not derivable* — only the provider knows whether the
> money actually moved. A production implementation would look the charge up **by
> `payment_id` at the provider**, and that lookup would also distinguish states this
> simulation has no need to represent: `PENDING` (still in flight) and `NOT_FOUND` (the
> provider never received it) are genuinely different from a settled result, and each
> demands a different action.
>
> What the simulation preserves faithfully is the **shape**: find stuck rows, ask an
> authority what really happened, apply the answer. Only the "ask an authority" step is
> stubbed.

**Step 3 — Apply the resolution, in a transaction.**

**BEGIN**, then:

> `SELECT status FROM payments WHERE id = $1 FOR UPDATE`

**A re-check of the status inside the transaction, under a row lock.** This closes the race
between the worker and everything else. Between the `SELECT` in Step 1 and this moment, the
original consumer may have finally completed Transaction 2, or a second worker replica may
have resolved the same row.

**If the status is no longer `PROCESSING`**, log `payment_already_resolved` and **skip this
row** — no update, no event. Without this re-check the worker would overwrite a legitimate
outcome and publish a **duplicate, possibly contradictory** `payment.succeeded` /
`payment.failed` into the saga.

Otherwise:

- `UPDATE payments SET status = $1, updated_at = NOW() WHERE id = $2`
- `INSERT INTO outbox_events` with the outcome topic, `key=<order_id>`, and a **freshly
  wrapped envelope** — a **new `event_id`**, distinct from anything the consumer would have
  produced.

**COMMIT.** Increment the count, log `stuck_payment_reconciled`.

> **Note the fresh `event_id`.** Order service's `processed_events` has never seen it, so
> the event *will* be processed rather than skipped as a duplicate. That is what makes
> recovery actually work — and it is also why Order's **state machine whitelist** is
> essential as the second line of defence: if the original Transaction 2 somehow *did*
> land as well, Order would receive two outcome events with different `event_id`s. The
> ledger cannot deduplicate them, but the whitelist rejects the second one because the
> order has already left `PENDING`.

### The complete recovery chain

> stuck `PROCESSING` row → worker detects it after 3 minutes → outcome re-derived from the
> persisted directive → status written **and** outbox row written in one transaction → the
> standard relay publishes it → Order service consumes it → the order finally leaves
> `PENDING`, and if the outcome was `FAILED`, Order emits `stock.release` and the stock
> comes back.

The saga completes normally, minutes late, using nothing but the ordinary machinery. The
worker does not have a special path into the saga — it simply produces the event that was
missing and lets everything downstream behave exactly as it always does.

## 6.1 TRACE A — THE HAPPY PATH

**Setup:** an authenticated user posts an order for 2 × Classic Burger. Stock is 100.
No `X-Payment-Simulate` header.

### Phase 0 — Authentication (once, earlier)

| # | Where | What happens |
|---|---|---|
| 0.1 | client → nginx `/auth/login` | nginx strips `/auth`, injects `X-Request-ID` and `X-Real-IP`, proxies to `auth-service:8001/login`. |
| 0.2 | auth: middleware | `RequestIdMiddleware` binds the request_id; `RateLimitMiddleware` INCRs `rate_limit:<ip>` in Redis, sets a 60 s TTL on the first hit, passes. |
| 0.3 | auth: handler | `SELECT … FROM users WHERE email`, then bcrypt verify. |
| 0.4 | auth: token | HS256 JWT minted with `sub`, `email`, `exp`=+15 min. A 64-byte refresh token is generated; its SHA-256 is inserted into `refresh_tokens`. |
| 0.5 | → client | `{access_token, refresh_token, token_type: "bearer"}` |

### Phase 1 — HTTP: the order is accepted

| # | Where | What happens |
|---|---|---|
| 1.1 | client → nginx `POST /orders` | `Authorization: Bearer <jwt>`. nginx preserves the path, injects `X-Request-ID`. |
| 1.2 | order: middleware | request_id bound. No rate limiter on this service. |
| 1.3 | order: JWT dependency | Token decoded locally with the shared secret. **No call to auth-service.** Yields `user_id`. |
| 1.4 | order: Pydantic | `restaurant_id` and `items` validated. |
| 1.5 | order: idempotency | No `Idempotency-Key` header → the lookup is skipped entirely. |
| 1.6 | order: compute | `order_id` = fresh UUID4 (application-side). `total_amount` = 2 × 9.99 = **19.98**. |
| 1.7 | order: envelope | `wrap_event("order.placed", {order_id, user_id, restaurant_id, items, total_amount})`. `event_id` = **E1**. No `payment_simulate` key, since no header was sent. |
| 1.8 | **order_db TXN** | **BEGIN** → `INSERT orders (status='PENDING')` → `INSERT outbox_events (topic='order.placed', key=order_id, payload=<E1>)` → **COMMIT** |
| 1.9 | → client | **202** `{id, status: "PENDING", message: "Order accepted for processing"}` |

> The customer now has an order ID. Nothing has been reserved and nothing has been charged.
> The event is still sitting in Postgres.

### Phase 2 — Order's relay publishes

| # | Where | What happens |
|---|---|---|
| 2.1 | order relay | Within 1 s: `SELECT … WHERE published_at IS NULL ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED` finds the row and locks it. |
| 2.2 | order relay | **BEGIN** → `send_and_wait("order.placed", key=order_id, value=E1)` → broker ACKs → `UPDATE outbox_events SET published_at = NOW()` → **COMMIT** |
| 2.3 | order relay | Next drain iteration finds nothing → returns 0 → the interruptible 1 s wait begins. |

### Phase 3 — Restaurant reserves the stock

| # | Where | What happens |
|---|---|---|
| 3.1 | restaurant consumer | `getmany` returns the message on `order.placed`. |
| 3.2 | **restaurant_db TXN** | **BEGIN** (outer). |
| 3.3 | idempotency | `SELECT 1 FROM processed_events WHERE event_id = E1` → nothing. Proceed. |
| 3.4 | **SAVEPOINT** | Nested transaction opened. |
| 3.5 | lock | `SELECT quantity FROM menu_item_stock WHERE item_id = <burger> FOR UPDATE` → **100**. Row locked for the rest of the transaction. |
| 3.6 | check | 100 ≥ 2 → satisfiable. |
| 3.7 | deduct | `UPDATE menu_item_stock SET quantity = quantity - 2` → now **98**. |
| 3.8 | record | `INSERT INTO stock_reservations (order_id, items)` — the items snapshot is stored so the compensation would know what to restore. |
| 3.9 | **RELEASE SAVEPOINT** | The nested block exits cleanly. |
| 3.10 | outbox | `wrap_event("stock.reserved", <the entire original payload>)` → `event_id` = **E2**. **`total_amount=19.98` is forwarded here** — this is the only way payment will learn the amount. `INSERT INTO outbox_events (topic='stock.reserved', key=order_id, payload=E2)`. |
| 3.11 | ledger | `INSERT INTO processed_events (E1)`. |
| 3.12 | **COMMIT** | Stock deduction, reservation record, outbox row, and ledger entry all land **atomically**. |

### Phase 4 — Restaurant's relay publishes

| # | Where | What happens |
|---|---|---|
| 4.1 | restaurant relay | Picks up the `stock.reserved` row under `FOR UPDATE SKIP LOCKED`. |
| 4.2 | restaurant relay | **BEGIN** → send E2 to Kafka, wait for ACK → mark `published_at` → **COMMIT** |

### Phase 5 — Payment charges (two transactions)

| # | Where | What happens |
|---|---|---|
| 5.1 | payment consumer | `getmany` returns the message on `stock.reserved`. Extracts `order_id`, `amount=19.98`, `payment_simulate=None`. |
| 5.2 | **payment_db TXN 1** | **BEGIN** → `SELECT 1 FROM processed_events WHERE event_id = E2` → nothing → `INSERT INTO payments (order_id, 19.98, 'PROCESSING', NULL) RETURNING id` → `INSERT INTO processed_events (E2)` → **COMMIT** |
| 5.3 | — | **The intent to charge is now durable on disk. The gateway has not been called yet.** |
| 5.4 | gateway | Directive is `None` → falls back to `PAYMENT_SIMULATE_DEFAULT` = `"success"` → not `"failure"` → returns **true**. |
| 5.5 | compute | status = `SUCCEEDED`, topic = `payment.succeeded`, envelope `{order_id}` → `event_id` = **E3**. |
| 5.6 | **payment_db TXN 2** | **BEGIN** → `UPDATE payments SET status='SUCCEEDED', updated_at=NOW()` → `INSERT INTO outbox_events (topic='payment.succeeded', key=order_id, payload=E3)` → **COMMIT** |

### Phase 6 — Payment's relay publishes

| # | Where | What happens |
|---|---|---|
| 6.1 | payment relay | Picks up the row, sends E3, waits for the ACK, marks published, commits. |

### Phase 7 — Order confirms

| # | Where | What happens |
|---|---|---|
| 7.1 | order consumer | `getmany` returns the message on `payment.succeeded`. |
| 7.2 | **order_db TXN** | **BEGIN**. |
| 7.3 | idempotency | `SELECT 1 FROM processed_events WHERE event_id = E3` → nothing. Proceed. |
| 7.4 | lock | `SELECT status FROM orders WHERE id = $1 FOR UPDATE` → **`PENDING`**. Row locked. |
| 7.5 | whitelist | `PENDING → CONFIRMED` is in the allowed set. Permitted. |
| 7.6 | write | `UPDATE orders SET status='CONFIRMED', updated_at=NOW()`. |
| 7.7 | ledger | `INSERT INTO processed_events (E3)`. |
| 7.8 | **COMMIT** | |

### Phase 8 — The client observes the result

`GET /orders/{id}` with the same JWT → ownership verified → **`status: "CONFIRMED"`**.

### Final state across all four databases

| Database | State |
|---|---|
| `order_db` | order = `CONFIRMED`; 1 outbox row (published); 1 processed_event (E3) |
| `restaurant_db` | burger stock = **98**; 1 `stock_reservations` row **still present**; 1 outbox row (published); 1 processed_event (E1) |
| `payment_db` | payment = `SUCCEEDED`; 1 outbox row (published); 1 processed_event (E2) |

> **The `stock_reservations` row is intentionally left behind on the happy path.** It is
> deleted only by the compensation. Its continued existence is the record that these units
> are legitimately consumed.

## 6.2 TRACE B — STOCK REJECTED (the saga aborts at step one)

**Setup:** an order for 200 × Milkshake. Stock is 50.

Phases 0–2 are **identical to Trace A** — the order is accepted, `PENDING`, and
`order.placed` (event **E1**) is published.

### Phase 3 — Restaurant refuses

| # | Where | What happens |
|---|---|---|
| 3.1 | restaurant consumer | Receives `order.placed` / E1. |
| 3.2 | **restaurant_db TXN** | **BEGIN** (outer). |
| 3.3 | idempotency | E1 not in `processed_events`. Proceed. |
| 3.4 | **SAVEPOINT** | Nested transaction opened. |
| 3.5 | lock | `SELECT quantity … FOR UPDATE` → **50**. |
| 3.6 | check | 50 < 200 → **raise `InsufficientStockError`**: "Insufficient stock for item …. Requested 200, available 50". |
| 3.7 | **SAVEPOINT ROLLBACK** | The exception escapes the nested block. Nothing was deducted; no reservation row was written. **The outer transaction is still alive.** |
| 3.8 | except | Caught **outside** the savepoint block. Logs `stock_reservation_failed`. |
| 3.9 | outbox | `wrap_event("stock.rejected", {order_id, reason})` → **E2'**. `INSERT INTO outbox_events (topic='stock.rejected', key=order_id)`. |
| 3.10 | ledger | `INSERT INTO processed_events (E1)`. |
| 3.11 | **COMMIT** | The rejection is durable. Stock is untouched at **50**. |

### Phase 4 — Relay publishes, Order aborts

| # | Where | What happens |
|---|---|---|
| 4.1 | restaurant relay | Publishes E2' on `stock.rejected`. |
| 4.2 | order consumer | Receives it. **BEGIN** → E2' not in the ledger → `SELECT status … FOR UPDATE` → `PENDING` → whitelist permits `PENDING → STOCK_UNAVAILABLE` → `UPDATE orders SET status='STOCK_UNAVAILABLE'` → `INSERT processed_events (E2')` → **COMMIT**. |

### Why there is no compensation here

The saga terminated **before any irreversible side effect occurred**:

- Stock was never decremented — the savepoint saw to that.
- No `stock_reservations` row exists.
- **The payment service never saw this order at all.** It only subscribes to
  `stock.reserved`, which was never published.

There is nothing to undo, so no compensating event is emitted. This is the cheapest failure
path in the system: two events total, one database write per service.

### Final state

| Database | State |
|---|---|
| `order_db` | order = `STOCK_UNAVAILABLE`; processed_event E2' |
| `restaurant_db` | stock **unchanged at 50**; **no** `stock_reservations` row; processed_event E1 |
| `payment_db` | **completely empty** — no payment row, no events |

## 6.3 TRACE C — PAYMENT FAILED (the full compensation)

**Setup:** an order for 2 × Classic Burger with header **`X-Payment-Simulate: failure`**.
Stock is 100.

### Phase 1 — HTTP, with the directive captured

Identical to Trace A, with two additions:

| # | What happens |
|---|---|
| 1.3a | `X-Payment-Simulate: failure` is read from the headers. |
| 1.7a | Because the header is present, **`payment_simulate: "failure"` is added to the event payload**. |
| 1.8a | The `orders` row is inserted with `payment_simulate='failure'` **in the same transaction** as the outbox row. |

Event **E1** now carries the directive.

### Phases 2–4 — Stock is reserved, exactly as in Trace A

| # | What happens |
|---|---|
| 2.x | Order's relay publishes E1. |
| 3.x | Restaurant locks the row with `FOR UPDATE`, deducts 2, stock **100 → 98**, inserts the `stock_reservations` row with the items snapshot. |
| 3.10 | `stock.reserved` (**E2**) is built by wrapping the **entire original payload — including `payment_simulate: "failure"`**. This is the second hop of the directive's journey. |
| 4.x | Restaurant's relay publishes E2. |

> **Stock is now committed as reserved in `restaurant_db`.** This is the irreversible-by-
> rollback side effect. Everything from here on exists to be able to undo it.

### Phase 5 — Payment declines

| # | Where | What happens |
|---|---|---|
| 5.1 | payment consumer | Extracts `amount=19.98` and **`payment_simulate="failure"`** from E2's payload. |
| 5.2 | **payment_db TXN 1** | **BEGIN** → E2 not in the ledger → `INSERT INTO payments (…, 'PROCESSING', **'failure'**) RETURNING id` → `INSERT INTO processed_events (E2)` → **COMMIT** |
| 5.3 | — | The directive is now **persisted**, which is what makes this order recoverable if the process dies in the next step. |
| 5.4 | gateway | Directive is `"failure"` → returns **false**. |
| 5.5 | compute | status = `FAILED`, topic = `payment.failed`, envelope `{order_id}` → **E3'**. |
| 5.6 | **payment_db TXN 2** | **BEGIN** → `UPDATE payments SET status='FAILED'` → `INSERT INTO outbox_events (topic='payment.failed', key=order_id, payload=E3')` → **COMMIT** |
| 6.1 | payment relay | Publishes E3'. |

### Phase 7 — Order fails the order AND issues the compensation

| # | Where | What happens |
|---|---|---|
| 7.1 | order consumer | Receives `payment.failed` / E3'. |
| 7.2 | **order_db TXN** | **BEGIN**. |
| 7.3 | idempotency | E3' not in the ledger. Proceed. |
| 7.4 | lock | `SELECT status … FOR UPDATE` → `PENDING`. |
| 7.5 | whitelist | `PENDING → PAYMENT_FAILED` permitted. |
| 7.6 | write | `UPDATE orders SET status='PAYMENT_FAILED'`. |
| 7.7 | **compensation** | `wrap_event("stock.release", {order_id})` → **E4**. `INSERT INTO outbox_events (topic='stock.release', key=order_id, payload=E4)`. |
| 7.8 | ledger | `INSERT INTO processed_events (E3')`. |
| 7.9 | **COMMIT** | **"This order failed" and "the stock will be released" become the same durable fact.** Neither can exist without the other. |

### Phase 8 — The compensation is published and applied

| # | Where | What happens |
|---|---|---|
| 8.1 | order relay | Picks up the `stock.release` row, sends E4 to Kafka with `key=order_id`, waits for the ACK, marks published, commits. |
| 8.2 | restaurant consumer | Receives `stock.release` / E4. |
| 8.3 | **restaurant_db TXN** | **BEGIN**. |
| 8.4 | idempotency | E4 not in the ledger. Proceed. |
| 8.5 | lookup | `SELECT items FROM stock_reservations WHERE order_id = $1` → found. **This is why the reservation table exists** — E4's payload carries only the order ID, so the items must come from restaurant service's own memory of what it took. |
| 8.6 | restore | `UPDATE menu_item_stock SET quantity = quantity + 2` → **98 → 100**. No `FOR UPDATE` needed: a relative addition is safe to interleave. |
| 8.7 | cleanup | `DELETE FROM stock_reservations WHERE order_id = $1`. This is what makes a *duplicate* `stock.release` no-op cleanly at step 8.5. |
| 8.8 | ledger | `INSERT INTO processed_events (E4)`. |
| 8.9 | **COMMIT** | |

### Final state — the system is back where it started

| Database | State |
|---|---|
| `order_db` | order = `PAYMENT_FAILED`; **2** outbox rows (`order.placed`, `stock.release`), both published; processed_event E3' |
| `restaurant_db` | burger stock back to **100**; `stock_reservations` row **deleted**; 1 outbox row (`stock.reserved`); processed_events E1 and E4 |
| `payment_db` | payment = `FAILED`; 1 outbox row (`payment.failed`); processed_event E2 |

### What this trace demonstrates

**Six events across four services, and the inventory ends exactly where it began.** No
distributed transaction was used, no service ever locked a row in another service's
database, and no service ever waited synchronously on another. The consistency is
*eventual* — for roughly 3–4 seconds, `restaurant_db` genuinely believed 2 burgers were
gone while `order_db` had no idea the payment would fail. That temporary inconsistency is
the **explicit price** the saga pattern pays in exchange for services that can be deployed,
scaled, and fail independently.

## 6.4 TRACE D — PARTIAL STOCK ROLLBACK (multi-item, the savepoint in action)

**Setup:** one order for **2 × Classic Burger (stock 100)** *and* **500 × Milkshake
(stock 50)**. The items are processed in the order they appear in the array.

Phases 0–2 are identical: the order is accepted as `PENDING`, and `order.placed` (E1) is
published.

### Phase 3 — Restaurant fails halfway through its own work

| # | Where | What happens |
|---|---|---|
| 3.1 | restaurant consumer | Receives E1. |
| 3.2 | **BEGIN** (outer) | |
| 3.3 | idempotency | E1 not present. Proceed. |
| 3.4 | **SAVEPOINT** | Nested transaction opened. |
| 3.5 | **item 1 — burger** | `SELECT quantity … FOR UPDATE` → 100. 100 ≥ 2 → OK. |
| 3.6 | **item 1 — deduct** | `UPDATE … quantity - 2` → **98**. **This write has really happened inside the transaction.** |
| 3.7 | **item 2 — milkshake** | `SELECT quantity … FOR UPDATE` → 50. |
| 3.8 | **item 2 — check** | 50 < 500 → **raise `InsufficientStockError`**. |
| 3.9 | **SAVEPOINT ROLLBACK** | The exception escapes the nested block. **The burger deduction at 3.6 is undone — stock returns to 100.** The `stock_reservations` insert was never reached. The outer transaction survives. |
| 3.10 | except | Caught outside the savepoint. |
| 3.11 | outbox | `stock.rejected` (**E2'**) with the milkshake's reason string. |
| 3.12 | ledger | `INSERT INTO processed_events (E1)`. |
| 3.13 | **COMMIT** | The rejection commits. **Both stock levels are exactly as they started: 100 and 50.** |

### Phase 4 — Order aborts

Identical to Trace B: order → `STOCK_UNAVAILABLE`. No compensation, because nothing was
ultimately deducted.

### Why this needs the savepoint and not just the outer transaction

The naive alternative is a single flat transaction. In it, the burger deduction at 3.6 and
the `stock.rejected` outbox row at 3.11 would be **the same unit of work**. You cannot
commit one without the other. So:

- **Commit** → the rejection is recorded, but **2 burgers are permanently gone**, deducted
  for an order that was rejected. And because no `stock_reservations` row was written, a
  later `stock.release` would find nothing and no-op — **the stock is lost forever, with
  nothing in the system able to detect it.**
- **Roll back** → the burger deduction is correctly undone, but **the `stock.rejected`
  event is undone with it**. Nothing is published. Order service sits in `PENDING`
  forever, and the Kafka offset advances past the message so it is never retried.

Both options are broken. The savepoint is what makes the third, correct option possible:
**roll back only the stock writes, keep the transaction alive, and then record the
rejection in it.**

> This is why the code comments insist the `except` clause stay *outside* the nested block.
> Catching `InsufficientStockError` inside it would mean the savepoint's context manager
> exits normally, **releases** rather than rolls back, and the partial deduction commits —
> restoring the exact "commit" failure mode above.

## 6.5 TRACE E — CRASH RECOVERY VIA RECONCILIATION

**Setup:** Trace C (`X-Payment-Simulate: failure`), but the payment service process is
killed immediately after Transaction 1 commits.

| # | What happens |
|---|---|
| 1 | Phases 1–4 complete normally. Stock is **98**. A `stock_reservations` row exists. `stock.reserved` (E2) has been consumed. |
| 2 | **payment_db TXN 1 commits**: `payments` row = `PROCESSING`, `payment_simulate='failure'`; `processed_events` contains E2. |
| 3 | **The process is killed.** The gateway was never called. Transaction 2 never ran. |
| 4 | The container restarts. Migrations re-run as no-ops. The consumer rejoins the group. |

### Why nothing else can recover this

| Mechanism | Why it cannot help |
|---|---|
| **Kafka redelivery** | Even if E2 were redelivered, Transaction 1 already wrote E2 into `processed_events` — the handler short-circuits at step 1.1 and does nothing. |
| **The outbox relay** | No outbox row was ever written; that only happens in Transaction 2. There is nothing pending to find. |
| **Order service** | Sits in `PENDING` waiting for an event that will never come. It has no timeout of its own. |

**Database state is the only surviving signal.**

### Recovery

| # | Where | What happens |
|---|---|---|
| 5 | reconciliation worker | Within 60 s of the next poll after the 3-minute grace period: `SELECT … WHERE status='PROCESSING' AND updated_at < NOW() - INTERVAL '3 minutes'` finds the row. |
| 6 | re-derive | Calls the gateway with the **persisted** `payment_simulate='failure'` → returns false → `FAILED`. **This is precisely what migration `002` exists for.** Without the persisted column the directive would fall back to `PAYMENT_SIMULATE_DEFAULT='success'` and the order would be silently, wrongly confirmed — with the stock never released. |
| 7 | **payment_db TXN** | **BEGIN** → `SELECT status … FOR UPDATE` → still `PROCESSING` (nothing else fixed it) → `UPDATE payments SET status='FAILED'` → `INSERT INTO outbox_events (topic='payment.failed', payload=<**new event_id E3''**>)` → **COMMIT** |
| 8 | payment relay | Publishes E3'' normally. |
| 9 | order consumer | E3'' has never been seen → passes the idempotency check → order `PENDING → PAYMENT_FAILED` → **`stock.release` (E4) written to the outbox in the same transaction**. |
| 10 | order relay → restaurant | E4 published and consumed → stock **98 → 100**, reservation row deleted. |

**The saga completes correctly, roughly three minutes late, using nothing but the ordinary
machinery.** The reconciliation worker has no special path into the saga — it simply
produces the event that went missing and lets every downstream component behave exactly as
it always does.

> **Why the fresh `event_id` matters, and why the whitelist backs it up.** E3'' is new, so
> Order's ledger cannot mistake it for a duplicate — which is what makes recovery work at
> all. But if the original Transaction 2 had *also* somehow landed, Order would now receive
> two outcome events with different `event_id`s. The ledger cannot deduplicate those. The
> **state machine whitelist** rejects the second one, because the order has already left
> `PENDING` and terminal states have no allowed transitions.

# PART 7 — FAILURE AND RECOVERY MATRIX

## 7.1 Where each failure is caught

| Failure | Caught by | Outcome |
|---|---|---|
| Crash between the order INSERT and the Kafka publish | **Transactional outbox** | Impossible by construction — they are one transaction. |
| Kafka broker down when the relay tries to publish | **Relay per-event transaction** | `published_at` stays NULL; retried every second until the broker returns. Nothing lost. |
| Crash after the Kafka ACK, before `published_at` is set | **Consumer `processed_events`** | The event is published twice with the same `event_id`; the second delivery is a clean no-op. |
| Consumer crashes mid-batch, before the offset commit | **`processed_events` + at-least-once** | The whole batch is redelivered; already-processed events no-op, unprocessed ones run. |
| Two orders race for the last unit of stock | **`SELECT … FOR UPDATE` on `menu_item_stock`** | They serialize; the second re-reads the committed quantity and is correctly rejected. |
| Multi-item order fails on a later item | **SAVEPOINT (nested transaction)** | Earlier deductions roll back; the outer transaction survives to record the rejection. |
| Duplicate `order.placed` with a *new* `event_id` | **`stock_reservations.order_id` UNIQUE** | The violation is caught by name and swallowed; stock is deducted exactly once. |
| Duplicate `stock.release` | **Empty-result no-op** | The reservation row is already deleted; logs a warning and returns without raising. |
| Payment service crashes around the gateway call | **Two-transaction split + reconciliation worker** | The `PROCESSING` row survives as a known-unknown; reconciled after 3 minutes. |
| Duplicate `POST /orders` (client retry) | **`Idempotency-Key` + UNIQUE constraint** | The original order and status are returned; no second order, no second event. |
| A stale outcome event arrives after the order is terminal | **State machine whitelist + `FOR UPDATE`** | `InvalidTransitionError`; the transaction rolls back with no state change. |
| Redis down | **Fail-open rate limiter** | Rate limiting is disabled and logged; authentication and ordering keep working. |
| Auth service completely down | **Stateless JWT verification** | Existing tokens keep working for their full 15 minutes; only new logins fail. |

## 7.2 What is deliberately **not** handled

These are real gaps, listed honestly. Each is a design boundary rather than an oversight,
but each is a genuine limitation.

| Gap | Consequence |
|---|---|
| **No dead-letter queue.** The offset commits after the whole batch, including messages that raised. | A permanently-failing message is skipped forever. It exists only as a log line and a `status="error"` metric increment. |
| **No prices validated against `menu_items.price`.** The client supplies the price and the order total is computed from it. | A client can order at any price it chooses. Stock is checked; value is not. |
| **No `quantity > 0` validation.** | A negative quantity produces a negative total and, downstream, a stock *increase* instead of a decrement. |
| **`/health` checks Postgres only.** | A service can report healthy while its Kafka consumer is dead and the saga is fully stalled. |
| **No timeout on `PENDING` orders.** Only *payments* have a reconciliation worker. | An order whose `order.placed` was consumed but which never produced any outcome event sits in `PENDING` indefinitely. `idx_orders_status` makes them findable; nothing acts on them. |
| **`GET /payments/order/{id}` has no auth and no ownership check.** | Anyone with an order ID can read its payment record through the public nginx route. |
| **The `type: "access"` JWT claim is never verified.** | Any token signed with the shared secret is accepted by the Order service, regardless of its intended type. |
| **HS256 is symmetric.** | Every service holding `JWT_SECRET` can mint tokens, not merely verify them. |
| **The expired-refresh-token cleanup delete is rolled back** by the `HTTPException` that follows it. | Expired rows accumulate in `refresh_tokens` and are never pruned. |
| **The rate limiter keys on the socket peer address**, which behind nginx is always nginx. | The 30-per-minute limit is effectively global rather than per-client in the composed deployment. |
| **Registration's existence check is not transactional.** | A simultaneous duplicate registration returns 500 (from the UNIQUE violation) rather than a clean 409. |
| **Redis never reconnects** after a successful connect followed by a failure. | Rate limiting stays off until the process restarts. |
| **Migrations cannot express destructive changes.** | Renames, drops, and backfills are not possible under the `IF NOT EXISTS` scheme. |

| restaurant | consumer | 1 s poll | Consume `order.placed`, `stock.release`. |
| payment | outbox relay | 1 s | Publish `payment.succeeded`, `payment.failed`. |
| payment | consumer | 1 s poll | Consume `stock.reserved`. |
| payment | **reconciliation worker** | **60 s** | Resolve payments stuck in `PROCESSING` for over 3 minutes. |

## 8.3 Every lock and constraint that enforces correctness

| Mechanism | Location | Protects against |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | outbox relay, all three services | Two relay replicas double-publishing the same event; and blocking each other. |
| `FOR UPDATE` on `menu_item_stock` | restaurant reservation | Overselling under concurrent orders. |
| `FOR UPDATE` on `orders` | order state machine | Lost updates from concurrent outcome events. |
| `FOR UPDATE` on `payments` | reconciliation worker | The worker overwriting an outcome that just landed. |
| `SAVEPOINT` (nested transaction) | restaurant reservation | Partial deductions committing on a multi-item failure. |
| `CHECK (quantity >= 0)` | `menu_item_stock` | Negative stock if the application check is bypassed. |
| `PRIMARY KEY (event_id)` | `processed_events` × 3 | Duplicate event processing. |
| `UNIQUE (order_id)` | `stock_reservations` | Double stock deduction for one order. |
| `UNIQUE (order_id)` | `payments` | Double charging one order. |
| `UNIQUE (idempotency_key)` | `orders` | Duplicate orders from client retries. |
| `UNIQUE (email)` | `users` | Duplicate accounts. |
| Transition whitelist | order state machine | Semantically conflicting outcome events reaching a terminal order. |
